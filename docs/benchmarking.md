## 1. Topology

Point-to-point fibre, **Intel X520 / 82599 10 GbE** on both ends.
No switch in the path — a switch adds latency, may apply flow control, and hides
the true NIC-to-NIC bandwidth.

**Example rig used for this campaign:**

| Role | Machine |
|------|---------|
| Generator (`dnsmark --xdp`) | Dual Intel Xeon E5-2690 v2 (2013, 20 cores / 40 threads) |
| Receiver (DNS under test) | AMD Threadripper PRO 5995WX |

Both machines run Linux with the `ixgbe` driver. The X520 exposes up to
**16 RSS queues** (hardware RETA limit of the 82599 — you cannot exceed this,
regardless of core count).

> **NIC choice — the X520 works but is not recommended for this benchmark.**
> The 82599 / `ixgbe` is usable end-to-end, but it is a poor *measurement*
> platform: in AF_XDP zero-copy its netdev counters (`rx_packets`,
> `rx_missed_errors`, `tx_packets`) read a delta of 0 under load, so wire
> throughput is only visible via `*_nic` driver counters and the per-socket
> `XDP_STATISTICS`; it is PCIe 2.0; and RSS is hard-capped at 16 queues. Prefer
> Intel i40e (X710), ice (E810) or igc for high-rate or reproducible
> measurements (valid zero-copy counters, PCIe 3.0+, no 16-queue cap).

## 2. NIC & Host Tuning

> **What `--xdp` does for you, generator-side:** CPU governor → `performance`,
> auto-confine to the NIC's NUMA node (CPU + memory, single-NIC — replaces `numactl
> --cpunodebind=N --membind=N`), source-port spread (internal, no `DNSMARK_SPORT_SPREAD`),
> RSS RETA spread across the worker queues, one busy-poll worker per NIC-local core, and
> firehose by default (`--max-outstanding 0`). So a generator run is just
> `dnsmark -s <ip> --xdp -d <corpus>`. The items below you still set **once** per host
> (flow control, ring size) and on the **receiver** (RSS, port :53) — they are not per-run.

Apply the following on **both** the generator and the receiver.
Each step has measurable impact — skipping any one will cap your throughput.

### 2.1 Disable flow control ← **Trap #1**

```bash
ethtool -A <nic> rx off tx off
```

802.3x PAUSE frames (generated by a saturated receiver) throttle the sender at the
MAC layer, silently. This is typically the single biggest bottleneck — an order of
magnitude of throughput hides behind it.

Always disable first, before touching anything else.

### 2.2 RSS — hash on L4 ports

```bash
ethtool -N <nic> rx-flow-hash udp4 sdfn
```

Most NICs default to hashing on IP addresses only (`sd`). With a single-source
generator (one source IP), all UDP traffic lands on **one RX queue → one core**,
collapsing throughput to a single core's worth. Adding source+destination ports
(`sdfn`) distributes load across all queues, so RX scales with active cores.

dnsmark fans queries across the receiver's RSS queues. In **kernel mode** each
worker sends from its own UDP source port (a kernel socket per `-c` worker). With
**`--xdp`**, each worker **cycles its source port over a wide range**
(`SPORT_SPREAD=2048`), so query traffic carries thousands of
distinct 5-tuples and spreads across the receiver's full RSS — run enough workers
to light up the queues. For single-queue / single-core testing, run a single worker
(`-c 1`).

### 2.3 RSS — spread across queues

```bash
ethtool -X <nic> equal 16
```

The 82599 caps RSS at **16 queues** (hardware limit — you cannot go higher).
Set this explicitly; the default spread may not be uniform.

> **Note (`--ramp --xdp`):** the ramp temporarily re-steers the RSS indirection
> table to a **single** RX queue (`ethtool -X <nic> equal 1`) for the duration of
> the ramp — it needs one continuously-drained queue to find the saturation knee,
> and it overrides the `equal 16` setting above without restoring it. This affects
> **ramp mode only**; flood and closed-loop modes use the full spread. Re-apply
> `ethtool -X <nic> equal 16` afterward if you continue with other modes.

### 2.4 Ring buffers at maximum

```bash
ethtool -G <nic> rx 4096 tx 4096
```

Small rings mean the NIC drops descriptors under burst — `rx_missed_errors` climbs
immediately. Max them out.

### 2.5 CPU governor + mandatory warm-up

```bash
# pin all concerned cores to performance governor
for cpu in /sys/devices/system/cpu/cpu*/cpufreq/scaling_governor; do
    echo performance > "$cpu"
done
```

With `schedutil` or `powersave`, the kernel under-clocks cores during the
micro-burst DNS hot path, measurably capping throughput. Switching the **same
binary** to the `performance` governor lifts the rate solely by keeping cores at
full clock during the burst — no code change involved.

**Warm-up rule:** flood for at least **15 seconds** before sampling. DVFS
transients, JIT compilation paths, and TLB cold-starts all resolve within that
window. Sample only after the throughput curve flattens. (dnsmark's own auto
warm-up default is **5 s**, so the reported rate is already steady-state; the 15 s
rule above still applies to hand-run `ethtool -S` deltas.)

## 3. Measuring Receiver Throughput Correctly

> **dnsmark reports this for you.** The summary line
> **`Server throughput (NIC rx)`** = `rx_packets + rx_missed_errors + rx_fifo_errors +
> rx_over_errors` on the generator's
> return NIC(s) — the authoritative server reply rate (it counts replies the kernel later
> drops at the socket, and adds back NIC ring-overflow drops). You no longer need the
> manual `ethtool -S` delta below; it is kept as the explanation of *why* that line is the
> truth and how to cross-check it on the **receiver** side.

> **Why NIC rx is the truth, not userspace round-trip:** the `Round-trip completed`
> counter can under-report a fast server when responses are funnelled onto one XSK
> queue whose drain rate is far below the arrival rate. The firehose RX
> spreads the RETA across all worker queues and counts per-queue, so round-trip now
> tracks the NIC-rx truth. If `Round-trip completed` is still below `Server throughput
> (NIC rx)` you are generator-RX-bound (kernel socket / NIC-ring overflow, or a
> non-NUMA-local stack) — dnsmark prints a NOTE and the NIC-rx figure (`server_rx_qps`)
> is authoritative. In kernel-UDP open-loop flood this is expected: the generator's
> kernel recv drops a large fraction of the replies, so round-trip reads well below
> `server_rx_qps` while `server_rx_qps` remains the true server rate.

### 3.1 Ground truth: receiver NIC counters

Run these on the **receiver** machine, snapshot twice, compute deltas:

```bash
ethtool -S <nic>
```

| Metric | Counter | Notes |
|--------|---------|-------|
| **RX actually drained** | `rx_queue_N_packets` (sum all N) | Packets the driver consumed from NIC |
| **TX responses emitted** | `tx_bytes_nic` ÷ ~87 bytes | ⚠️ `tx_packets` / `tx_bytes` stay at **0** with AF_XDP zero-copy — only `tx_bytes_nic` (NIC-level counter) captures ZC TX |
| **NIC-level drops** | `rx_missed_errors` | NIC received frame but host had no descriptor ready |

**Packet balance:** `offered ≈ drained + missed`

Measurement window: 10 seconds is sufficient; 30 seconds is better for stability.

### 3.2 Automating the delta

```bash
# snapshot
ethtool -S <nic> > /tmp/nic_before.txt
sleep 10
ethtool -S <nic> > /tmp/nic_after.txt

# parse rx_queue_N_packets (example — adapt grep to your driver output)
paste /tmp/nic_before.txt /tmp/nic_after.txt | \
  awk '/rx_queue_[0-9]+_packets/ { before=$2; getline; after=$2; total+=after-before } END { print total/10, "pps" }'
```

### 3.3 Line-rate awareness — is the wire or the server the limit?

> **Scope: the line-rate line and verdict are emitted for fixed/flood runs only,
> never in `--ramp`.** In a fixed/flood run `server_rx_qps` reflects one steady
> window, so the line-rate % is meaningful. In `--ramp`, `server_rx_qps` spans the
> whole ramp-up and its average sits far below the peak, so a line-rate % there
> would contradict the DSD's own **Capacity** summary — in ramp mode the DSD
> Capacity / Within SLO / Knee bracket is the throughput answer, and dnsmark omits
> the line-rate line (`line_rate` is `null` in `--ramp` JSON).

The NIC-counter truth above (`server_rx_qps`, §3) tells you the authoritative
server reply rate. dnsmark **builds directly on that number** to answer the next
question, from its own hardware observations, without reading anything on the
receiver side: *is this run limited by the Ethernet link, or by the server?*

dnsmark divides `server_rx_qps` by the line-rate ceiling it computes from the
average on-wire reply size (the egress NIC's `rx_bytes ÷ rx_packets`) and that
NIC's link speed, yielding **% of line rate** and a verdict:

- **wire-bound** (≥ 90 % of line rate) — the link is the limit; a faster server
  cannot help, you need a faster/second NIC.
- **link-headroom** (< 90 %) — the wire is not the wall; the server (or the
  generator) is.

In the text report (fixed/flood only) this appears as the throughput block's
`Line rate:` line followed by a verdict, e.g.:

```
Send throughput (egress):    9847000 qps
Wire egress (NIC PHY):       9852000 qps  (confirmed transmitted)
Round-trip completed:        9840000 qps  (99.9% of egress, userspace)
Server throughput (NIC rx):  9851000 qps  (authoritative — replies on the wire)
Line rate:                   100% of 10 Gb/s wire  (103 B replies, ceiling 9.85 M/s)
  → WIRE-BOUND: the 10 GbE link is the limit, not the server
```

(`Wire egress (NIC PHY)` is an XDP-only line; kernel-UDP runs omit it.)

`--json` adds a `line_rate` object (null in `--ramp`):

```json
"line_rate": {
  "avg_reply_bytes": 103,   // NIC rx_bytes / rx_packets, on the wire
  "line_rate_pps": ...,     // computed ceiling
  "link_mbps": 10000,
  "percent_of_line": ...,
  "rate_qps": ...,          // = server_rx_qps, the authoritative figure
  "verdict": "wire-bound"   // or "link-headroom"
}
```

This is self-contained (no receiver-side reading) and works identically in
AF_XDP and kernel-UDP mode (fixed/flood runs — see the scope note above); it
reuses the same `server_rx_qps` reference — it does not replace or contradict
it.

**On 10 GbE, DNS at multi-Mpps is line-rate bound.** For ~100 B replies a single
10 G NIC tops out at roughly its per-frame pps ceiling (see §4.2), and both
directions pin to the wire once the server is fast enough to fill it. The exact
ceiling is reply-size dependent — smaller mean replies raise the pps ceiling —
which is why a run's `line_rate` verdict is computed from the *observed* average
on-wire reply size rather than a fixed constant.

**The wire is the wall — not the CPU, not PCIe.** A *single* core can saturate a
10 G NIC in **both** directions (TX and RX-count): a 1-core unified worker and a
2-core TX/RX split give identical throughput. PCIe is not the constraint either —
x8 Gen3 is ~63 Gbps, roughly 6× a single 10 G link. Once a run reports
**wire-bound**, adding cores or optimizing the DNS logic buys nothing; the only
lever left is more/faster NICs.

## 4. Interpreting Results

### 4.1 Are you CPU-bound?

```bash
mpstat -P <cores> 1 5
```

- Cores **≥ 90% busy** AND `rx_missed_errors` flat → **CPU-bound** → optimize code / add cores.
- Cores **< 90% busy** AND `rx_missed_errors` climbing → **not CPU-bound** → bottleneck is
  fill-ring throughput, UMEM allocation, or NIC descriptor pressure. CPU optimization is wasted here.

### 4.2 Physical line-rate ceiling

For a typical DNS response on 10 GbE:

```
Ethernet (14) + IP (20) + UDP (8) + DNS payload (~60) + FCS (4)
  + preamble (8) + IFG (12) = ~126 bytes on the wire per direction

For a ~111-byte frame: 10 Gbps ÷ (111 × 8 bits) ≈ 11.3 M pps
```

This is a **hard physical limit**. Beyond it, you need 25/40/100 GbE — no amount
of code optimization helps. The exact figure scales with frame size: smaller
query frames on the TX side push the pps ceiling slightly higher, larger replies
lower it.

### 4.3 Use medians, not peaks

Absolute numbers vary run-to-run even with the governor pinned (thermal state,
other tenants on a shared host, NUMA effects). Do not compare numbers across
different sessions. **Compare ratios within a single session** (e.g., A vs. B
dos-à-dos). Use **medians** from multiple samples, not the peak reading.

## 5. Gotchas

### 5.1 ARP-unresolved TX fallback

When the server's MAC address is not ARP-resolved, dnsmark cannot build zero-copy
frames and **falls back to the kernel `sendmmsg` path**, emitting a loud `WARN`.
`Queries sent` increments normally, but **nothing leaves the NIC over zero-copy**:
`tx_bytes_nic` on the generator stays flat. Always verify `tx_bytes_nic` on the
generator side.

```bash
# workaround: pin the ARP entry permanently
ip neigh replace <server-ip> lladdr <server-mac> dev <nic> nud permanent
```

### 5.2 Corrupted NIC/XDP state after repeated runs

Repeated attach/detach of XDP programs, or changing the channel count while XDP
is active, can leave the NIC in a broken state where throughput collapses
(sometimes to near zero) without any error message.

**Reset procedure:**

```bash
ip link set <nic> down
ip link set <nic> up
# then re-apply full tuning (ethtool -A, -N, -X, -G)
```

This clears the stuck XDP state. Always do this after changing `ethtool -L`
channel counts.

### 5.3 The poll-model myth

Switching a worker loop from **poll-first** to **drain-first** does **not**
increase throughput under saturation. `poll()` returns immediately when packets
are already in the ring — its timeout only matters at idle (latency impact).

General rule: **measure the actual bottleneck before writing code.** Use
`rx_missed_errors` + `mpstat` to identify the real constraint; don't guess.

### 5.4 RSS cap at 16 queues (82599)

The 82599 RETA table has 128 entries but only **16 unique queues**. You cannot
spread RX beyond 16 physical cores on this NIC, regardless of `ethtool -X`
arguments or core count. This is a hardware limit, not a driver bug.

### 5.5 Reading `--ramp` (auto-DSD) output

`--ramp` (and the bare auto-run: no `-Q`, no `-l` ⇒ auto-DSD capacity
discovery) probes for the saturation knee by **doubling-then-bisecting** (DSD:
an exponential-growth phase followed by a bisection between the last good and
first bad rate), gated by an auto-derived latency SLO — and, in kernel-UDP, also
by delivered throughput (a step counts as saturated once the NIC-served rate
falls below ~80 % of the target, since the closed loop keeps latency flat past
that point; `--xdp` stays latency-only). It prints one line per
step and a plain-English summary:

```
Ramp step: offered 2000000 q/s | served 1998400 q/s | rtt-samples 41230 | p50 0.21 ms p95 0.38 ms p99 0.55 ms
...
Idle latency: 0.14 ms (floor — minimum p50 observed)
Capacity:  9850000  (NIC-verified — max replies/s on the wire)
Within SLO:  9720000  (p50 stays under 0.90 ms at this rate)
Knee bracket (DSD bisection): [9600000 ; 9900000] q/s  (±1.5%)
```

The **Capacity** label depends on transport (see §5.6): in `--xdp` it is the
true wire max; in kernel-UDP it is the closed-loop knee, and the summary adds a
`Within SLO … dnsperf-comparable in kernel-UDP` note plus a pointer to the
open-loop command. The line-rate line and verdict from §3.3 do **not** appear in
`--ramp` — the DSD Capacity / Within SLO / Knee bracket is the throughput answer.

To publish a single steady number, confirm the ramp's Capacity at a fixed rate
over the full duration:

```bash
# take the ramp's reported Capacity <C> and verify it holds at a fixed rate:
dnsmark -s <ip> -Q <C> -l 30
```

### 5.6 kernel-UDP ramp Capacity is the closed-loop knee, not the raw ceiling

The `--ramp` / auto-DSD **Capacity** figure means different things in the two
transports, and conflating them under-reports the server by a large factor
(several-fold).

**kernel-UDP ramp is a gated closed loop** (dnsperf-comparable, latency-honest):
each outstanding query holds a slot until its reply is drained. The generator's
own *kernel* receive path drops replies under load, so those slots never free,
which clogs the outstanding budget and caps the **offered** rate well below the
server's real capacity — typically several-fold below the open-loop NIC-verified
figure. The resulting DSD figure is therefore the closed-loop SLO knee —
**generator-recv bound** — not the server's raw ceiling. It is
labelled accordingly:

```
Capacity: … (closed-loop knee — kernel-recv bound, NOT the server's raw max)
```

and the ramp prints a pointer to the open-loop command that reports the raw
ceiling:

```bash
# raw server ceiling — open-loop firehose, reports "Server throughput (NIC rx)"
# = server_rx_qps (the authoritative reply rate, §3):
dnsmark -s <ip> -Q 0 --max-outstanding 0
```

Across the three figures a kernel-UDP flood exposes on the same server:

- **ramp / auto-DSD (closed loop)** reports the SLO knee — bound by the
  generator's kernel-recv, the lowest of the three.
- **open-loop flood — `server_rx_qps` (NIC rx)** is the server's true rate,
  NIC-verified, and the highest of the three.
- **open-loop flood — userspace round-trip** sits between them: the generator's
  kernel recv drops a large fraction of the replies, so it counts well under
  `server_rx_qps`.

kernel-UDP is **generator-recv bound** — the generator serves and the server
replies far faster than the generator's kernel recv can drain. Removing exactly
that bound (a lossless zero-copy RX) is what `--xdp` exists for.

**The `--xdp` ramp is unaffected.** It is an open-loop firehose with a lossless
zero-copy RX, so its **Capacity** genuinely *is* the maximum replies/s on the
wire — no closed-loop cap sits between the generator and the server. Its Capacity
is line-rate / wire-bound (§3.3, §4.2) and needs no relabelling.

## 6. Reference Result — four-server cross-generator campaign, 2026-07-03

**This is the current, primary reference result.** Four DNS servers in strict
parity, driven by four different generators, all scored by the same NIC-tx truth.

**Rig:**

| Role | Machine |
|------|---------|
| Generator | Dual Intel Xeon E5-2690 v2 (20c/40t) |
| Receiver (DNS under test) | AMD Threadripper PRO 5995WX |
| Link | direct 10 GbE DAC, **single-link** Intel X710 (`i40e`), target `10.71.10.1` |

**Server parity (identical config on all four):** forward + cache to
1.1.1.1 / 8.8.8.8 / 9.9.9.9, DNSSEC **off**, `minimal-responses`, large cache. The
100k-domain corpus is **warmed first**, so every measured query is a cache hit.
Servers: BIND9 9.x, Unbound 1.22, Runbound `xdp:no`, Runbound `xdp:yes`.

**Generators (four load disciplines):**

| Generator | Model | Command shape |
|---|---|---|
| dnsperf | closed-loop, kernel-UDP, latency-bounded | `-c 500 -T 20 -q 100000` |
| dnsmark-udp | open-loop kernel firehose | `-Q 6M --max-outstanding 0` |
| dnsmark-xdp | open-loop AF_XDP firehose | `--xdp -Q 13M --max-outstanding 0` |
| kxdpgun 3.4.6 | open-loop AF_XDP firehose | `-Q 13M` |

**TRUTH = receiver NIC `tx_packets` delta ÷ 20 s** — the replies the server
actually put on the wire, the datapath- and tool-independent measure (§3). dnsmark
also self-reports this as `server_rx_qps`.

**Server throughput (qps, measured at the receiver NIC tx):**

| Server | dnsperf | dnsmark-udp | dnsmark-xdp | kxdpgun |
|--------|--------:|------------:|------------:|--------:|
| BIND9 9.x | 711 k | 1.89 M | 872 k | 1.03 M |
| Unbound 1.22 | 1.55 M | 2.57 M | 3.06 M | 2.80 M |
| Runbound (xdp:no) | 1.26 M | 3.40 M | 6.81 M | 5.50 M |
| Runbound (xdp:yes) | 1.65 M | **5.27 M** | **12.5 M** | 10.1 M |

**Server ceiling ranking** (peak over generators): Runbound `xdp:yes` **12.5 M**
> Runbound `xdp:no` **6.8 M** > Unbound **3.1 M** > BIND9 **1.9 M**. Runbound-xdp
is **~6.6× BIND9**, **~4.1× Unbound**, and **~1.8× its own kernel mode** —
Runbound's AF_XDP fast path roughly **doubles** its own kernel-path throughput.

**Generator discipline matters — and this is why we score at the NIC.** The
open-loop AF_XDP generators (dnsmark-xdp, kxdpgun) drive a *robust* server hardest
— **except BIND9, which collapses under the 13 M XDP firehose** (872 k / 1.03 M vs.
1.89 M under the gentler kernel-UDP dnsmark). That is classic **receiver livelock /
overload**: at extreme ingress BIND9 burns all CPU in softirq and drops, and so
*processes less* at a higher offered rate than at a lower one. The receiver NIC
`tx_packets` counter captures the truth regardless of which generator produced it —
which is exactly what makes cross-tool numbers comparable. A benchmark's headline
number is therefore as much a property of the **generator's load discipline** as of
the server. Corollaries visible in the table:

- **dnsperf** (closed-loop, latency-bounded) is consistently the **lowest** — it is
  a latency tool, not a saturation tool, so it never offers enough load to find a
  robust server's ceiling.
- **dnsmark `--xdp`** is the strongest saturation generator on the three robust
  servers (Unbound, both Runbound modes).

**Caveats (stated honestly):** these are **single 20 s runs** — expect **±10–15 %**
run-to-run; they are **not averaged** (§4.3 still applies: publish medians for
anything comparative). The Runbound `xdp:yes` **12.5 M** figure exceeds the
~9.85 M/s line-rate ceiling quoted elsewhere for 103 B replies because **this warm
produced smaller average replies** — the line-rate ceiling is reply-size dependent
(§3.3, §4.2), so a smaller mean reply raises the pps ceiling. All figures are the
receiver-NIC-tx truth.

## 7. Latency accuracy — what a generator actually measures

Every closed-loop DNS generator reports a round-trip time that is the **sum of three
independent terms**:

```
reported RTT  =  server processing  +  network round-trip  +  generator client-side overhead
                 (on the wire)          (link + both NICs)     (build / send / recv / timestamp
                                                                inside the tool itself)
```

Only the **first** term is a property of the server. The **third** is a property of the
*tool* — its send/receive loop and where it places its timestamps — and it differs
between any two generators. dnsmark (default UDP path) is a closed-loop generator over a
UDP kernel socket; that third term is its own, so its **absolute** number sits above the
server's wire time even against the same server. That is inherent to any closed-loop
generator and is **not a defect** — the goal here is only to make the three terms explicit
and measurable, so an absolute latency is never misread as a server property.

### Ground truth for the server's term: the wire

The server's own contribution is measured **on the server**, independent of any
generator, by pairing each query with its response by DNS transaction id:

```bash
# on the server under test, during the run
tcpdump -i <iface> -tt -nn udp port 53
#   query (dst :53) -> response (src :53), matched by txid; the delta is the server's
#   processing time — the wire term above, nothing else.
```

The wire is ground truth for the *server's* term — not for what an application sees: a
real kernel-UDP client carries stack overhead too.

### Decomposition — what to expect

Measure it yourself with the commands below (`-Q 100000`, 100 outstanding, 4 clients;
`dnsmark` on its default UDP path), pairing the generator's reported RTT against the
server's own wire time from a txid-matched capture. Two facts hold in every direction
(generator and receiver swapped):

1. **dnsmark always reports more than the wire** — necessarily, since the RTT contains the
   server's own time. It never under-reports; there is no value below the server's floor.
   The gap (`dnsmark − wire`) is dnsmark's client-side overhead — kept light by the
   batched `recvmmsg` drain and a tight send/poll loop.
2. **The offset is generator/rig-dependent, but stable across servers for a fixed
   generator.** It is larger on a fast generator's lean loop, smaller on an older CPU;
   crucially, on one fixed rig it barely moves between servers, so server **rankings are
   preserved** — the comparison that matters.

### Consequences for a benchmark

- **Never quote a generator's absolute latency as "the server's latency."** It is a
  property of the *(server, generator, rig)* triple. Cite the **wire** for the server's
  own term.
- **Compare servers with one fixed generator on one rig.** The tool/rig overhead is then
  a constant that cancels in the comparison.

### Reproduce it

One command per server plus a capture — anyone can re-derive the numbers above on their
own hardware:

```bash
# generator — pick ONE rig and use it for every server you compare
dnsmark -s <server> -d corpus.txt -c 4 --max-outstanding 100 -Q 100000 -l 6 --json
# server — ground truth for its own term, paired by txid -> p50
tcpdump -i <iface> -tt -nn udp port 53
```
