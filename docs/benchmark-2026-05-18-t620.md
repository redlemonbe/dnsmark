## 2. Méthodologie

Toutes les requêtes sont générées en mode `--random` : sous-domaines UUID aléatoires sous `bench.invalid.` (type A).  
Ce mode force le serveur à effectuer une **résolution récursive complète** pour chaque requête, sans aucun cache pouvant biaiser les résultats.  
La réponse attendue et correcte est `NXDOMAIN` (domaine inexistant).

Protocole : **UDP port 53** (standard DNS).  
Voie de réception : **AF/XDP** — les réponses UDP src_port=53 sont capturées au niveau du pilote NIC via eBPF, sans passer par la pile réseau du kernel.

```
dnsmark -s 192.168.1.10 --random [options]
```

## 3. Résultats

### Phase 1 — Sondage initial (5 s, unlimited)

Objectif : vérifier la connectivité et estimer l'ordre de grandeur.

```
dnsmark -s 192.168.1.10 --random -l 5 -q --no-tui
```

| Métrique | Valeur |
|---|---|
| Requêtes envoyées | 309 189 |
| Requêtes complétées | 309 079 |
| Taux de complétion | **99.96 %** |
| Débit mesuré | **61 755 QPS** |
| Latence min | 0.010 ms |
| Latence moy | 2.372 ms |
| p50 | 1.229 ms |
| p95 | 5.831 ms |
| p99 | 17.615 ms |
| p999 | 47.903 ms |
| Latence max | 53.823 ms |

**Observation :** le serveur absorbe sans effort 62 000 requêtes/s avec un taux de perte quasi nul et une latence médiane sous 1.3 ms. Pas encore saturé.

---

### Phase 2 — Ramp mode (montée progressive jusqu'à saturation)

Objectif : trouver le QPS maximal supportable par doublement toutes les 5 s.

```
dnsmark -s 192.168.1.10 --random --ramp --no-tui
```

| Palier cible | QPS burst mesuré | Saturé ? |
|---|---|---|
| 2 000 | 59 370 /s | Non |
| 4 000 | 55 376 /s | Non |
| 8 000 | 47 191 /s | Non |
| 16 000 | 48 063 /s | Non |
| 32 000 | 34 867 /s | Non |
| 64 000 | 54 694 /s | Non |
| 128 000 | **36 440 /s** | **Oui** (< 80 % cible) |

**Saturation déclarée : 64 000 QPS**

Le serveur tient 64 000 QPS de manière stable. À 128 000 QPS cible, le burst mesuré chute à 36 440 /s — le seuil de saturation est franchi.

Statistiques globales du ramp :

| Métrique | Valeur |
|---|---|
| Durée | 40 s |
| Requêtes envoyées | 896 244 |
| Requêtes complétées | 896 085 |
| Taux de complétion | **99.98 %** |
| Latence p99 | 20.399 ms |
| Latence p999 | 78.335 ms |

---

### Phase 3 — Saturation totale (flood sans limite, 30 s)

Objectif : dépasser massivement la capacité du serveur, mesurer la dégradation.

```
dnsmark -s 192.168.1.10 --random -l 30 -q --no-tui --max-outstanding 0
```

`--max-outstanding 0` : supprime le plafond de requêtes en vol — dnsmark envoie aussi vite que le NIC et le CPU le permettent.

| Métrique | Valeur |
|---|---|
| **QPS envoyé** | **~410 000 /s** |
| Requêtes envoyées (30 s) | 12 323 436 |
| Requêtes complétées | 359 415 |
| **Taux de perte** | **97.08 %** |
| QPS répondu | 11 978 /s |
| Latence moy | 153 ms |
| p50 | 106 ms |
| p95 | 459 ms |
| p99 | 706 ms |
| **p999** | **1 050 ms** |
| Latence max | 1 758 ms |

**Observation :** à 410 000 requêtes/s, la cible répond à seulement ~12 000 /s.  
97 % des paquets UDP sont perdus — les buffers réseau et applicatifs sont saturés.  
La latence explose : p999 > 1 seconde, max > 1.7 seconde.  
**Le serveur est à genoux.**

---

### Phase 4 — Test à 70 000 QPS (interrompu)

```
dnsmark -s 192.168.1.10 --random -l 30 -q --no-tui -Q 70000
```

**Résultat : crash de la VM cible.**  
Le test n'a pas abouti — la machine virtuelle hébergeant Runbound s'est arrêtée.  
Cause probable : saturation des ressources CPU/RAM du nœud Proxmox sous la charge combinée des phases précédentes, ou OOM sur la VM.

## 5. Conclusions

### Ce que le T620 (VM) peut absorber

- **~60 000–64 000 QPS** en mode récursif pur (cache froid, résolution complète à chaque requête)
- Latence médiane < 1.3 ms, p99 < 20 ms à charge nominale
- Zéro perte significative jusqu'au seuil

### Limites observées

- La limite observée est **celle de la VM**, pas du matériel T620.
  Proxmox alloue une fraction des ressources du T620 à la VM.
  En baremetal, les capacités seront significativement plus élevées.
- Le flood à 410k QPS montre que **le réseau actuel** (non-fibre) constitue lui aussi un goulot — les cartes Intel 10G non encore câblées changeront la donne.

### Prochaine étape — benchmark baremetal + fibre 10G

| Scénario | Estimation |
|---|---|
| T620 baremetal (Runbound, 20c physiques) | 500 000 – 1 000 000 QPS |
| T620 baremetal + XDP kernel-bypass | 1 000 000+ QPS (limité par la fibre 10G) |
| Limite physique fibre 10G (paquets 64B UDP) | ~14 880 000 QPS |

Le Threadripper PRO 5995WX en face a largement la capacité d'envoyer à 14M QPS — le vrai plafond sera le T620 et la fibre.
